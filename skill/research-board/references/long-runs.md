# 长任务：训练、评测、数据处理

## 先问
- 启动训练或任何占用显卡的任务前，先问用户，说明打算用哪台服务器、哪几张卡。可以叠加在已有任务的卡上，但要看显存够不够。
- 给别人留卡：独占的卡同时不超过该服务器总卡数的一半；叠加使用时可以适当放宽。
- 用户已经批准的范围（例如一条已采纳的决定写着「夜里本项目最多 4 张卡」）之内可以直接用，超出就写待办问用户。

## 怎么启动
- 一律在目标服务器的 tmux 里启动，会话名用 `<项目名>-<运行编号>`，不要挂在 ssh 前台。操作 tmux 时用 `-t =<名字>` 精确匹配。
- 用 boardrun 启动，它在 `board/runs/<运行编号>/` 里记下服务器、卡号、进程号、tmux 会话名、时间、状态、代码提交号、续自哪次运行，并每分钟写心跳。用法和 `run.json` 的格式见 `board-format.md` 的 run.json 一节。
  - 项目里安装：`uv add --editable <工具目录>/boardrun`。
  - Python 脚本里 `with boardrun.Run(attempt=..., kind="train", config=cfg) as run:`；不是 Python 的命令用 `python -m boardrun run --attempt <id> -- <命令>`。
  - 代码要先提交：有未提交的代码改动时 boardrun 拒绝启动（`board/`、`NOTES.md`、`REPORT.md`、`CLAUDE.md` 这些记录改了不算）。
  - 核心实验要先有预期：尝试标了 `core: true`、一页纸的「预期」却是空的或「用户没写」时，boardrun 拒绝启动，照它的提示先问用户（跳过的写法见 `board-format.md` 的「核心实验」）。
- 非交互 ssh 下 PATH 里可能没有 `uv`、conda 等，脚本里用完整路径。

## 状态和收尾
- 状态取值：运行中、完成、失败、被中断。boardrun 启动的运行，进程不在了由控制台所在机器上的收尾程序（`board reconcile`）自动标为被中断；手写记录的运行由会话核对后收尾：跑完了补状态和指标，没跑完标被中断。
- 失败也要记：运行失败或被中断后，把经过和原因写进它所属实验的「结果」。30 分钟后实验记录还没改，收尾程序会留一条待办给用户（见 `board-format.md` 的 todos.jsonl）。
- 等训练不守着：启动后把任务卡改成「等运行」，写好交接，会话就可以结束；运行都结束后收尾程序把卡改成「可以继续」。不要定时唤醒自己去查进度。

## checkpoint 和换服务器
- 训练脚本必须支持从 checkpoint 恢复；换服务器就是在这台停掉、在那台续跑。
- checkpoint 先写临时文件再改名（共享盘可能是 soft 挂载，网络抖动时写入会直接报错）。
- 换服务器：停掉原任务，在新服务器从 checkpoint 续跑，新的运行记录里写明续自哪次运行（`resumed_from`）。
- 大输出放 `results/<运行编号>/`，checkpoint 放 `ckpt/<运行编号>/`；控制台不显示它们，只给路径。训练结束后只保留被选用的 checkpoint，其余列出来问用户是否删除。
