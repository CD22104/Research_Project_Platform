# 进度记录格式（board/）

各项目 `board/` 目录的正式格式，由「CD的研究控制台」读取展示。这是唯一的正式版本：各项目的 `board/FORMAT.md` 只写一行指向本文件，不再各自维护一份。

- 正式版：a100 上 `~/gpu-board/docs/board-format.md`，随控制台代码一起改。
- 共享盘副本：`/shared/ssd/dchen/_shared/BOARD_FORMAT.md`，由 `scripts/publish-format.sh` 生成，不要手改。

格式还在试点，会调整；调整时先改本文件，再改控制台代码。

## 最少要写什么

新项目只需要两样就能在控制台里出现并可用：

1. `board/project.json`（标题、问题、状态）
2. `board/attempts/` 里的尝试记录

`setup.json`（实验设置：目标、数据集、模型、指标、方法的定义）在建项目时就写，之后每次更新整体方案（`plan.md`）或定新版本时同步更新，不要等到有结果再补。

其余文件都是可选的，有了就显示，没有就不显示，不会报错。建议在项目推进中逐步补上，大致顺序：`tracks/` 和 `versions/` → `runs/` → `examples/` → `flow.json`、`todos.jsonl`。

## 目录

```
board/
  project.json        项目本身：标题、问题、结论、状态、当前版本；可选 display
  setup.json          实验设置：目标、数据集、模型、指标、方法的定义（论文里的「实验设置」）
  plan.md             整体方案
  flow.json           项目流程图
  todos.jsonl         留给用户的待办
  versions/<id>.md    版本：每次定版的方案
  tracks/<id>.md      支线：一个方向上的一串尝试
  attempts/<日期>-<名字>.md   尝试：一次具体的实验
  runs/<运行编号>/run.json    运行：一次训练、评测或数据处理；可选 metrics.jsonl、samples.jsonl、图片
  examples/walkthrough.md     「一个例子」：一条样例从头走到底
  examples/probe.jsonl        固定的观察样例
  method/<步骤>.md            方法：从输入到输出的每一步怎么做，可以有不同做法和子流程
  tasks/<id>.md               任务卡：agent 要做的一件具体的事（工作视图）
  decisions/<id>.md           决定：用户定下的事，候选 → 用户在控制台采纳后生效
  docs/*.md                   文档：开头写 about（属于哪一步）和 kind（类型）；讨论纪要也在这里
  answers.jsonl  marks.jsonl  控制台写的：你的回复和文档标记（会话只读）
```

项目目录本身（`board/` 旁边）固定这样分：

```
<项目>/
  CLAUDE.md  NOTES.md  REPORT.md（可选）  pyproject.toml  uv.lock
  src/  scripts/  configs/        代码
  data/                           自建数据
  results/<运行编号>/              大输出：完整预测、日志、中间文件（控制台不显示，只给路径；boardrun 的 output_dir()）
  ckpt/<运行编号>/                 checkpoint
  board/                          控制台显示的一切：小而整理过的记录
```
放进 `board/` 的文件一分钟内出现在控制台上，不需要别的「上传」步骤；不想给控制台看的东西不要放进 `board/`。

另外，项目根目录（`board/` 旁边）的 `NOTES.md`（进度笔记）和 `REPORT.md`（总报告）会显示在「文档」页。控制台只读这两个固定文件名，不读根目录的其他文件。

**状态以 `board/` 为准。** 项目现在在做什么、跑了什么、结论是什么，都写在 `board/` 里，控制台从这里生成总览。`NOTES.md` 只放两样：换会话时的交接，和环境说明（怎么装环境、在哪台机器怎么跑、踩过的坑），不再另记一份进度，免得和 `board/` 对不上。

## 两个视图

控制台把一个项目分成两个视图，记录也按这个分：

- **研究视图**：研究本身。方法（`method/`）、实验（版本 → 支线 → 尝试 → 运行）、样例、实验设置、文档。
- **工作视图**：谁在做什么。任务卡（`tasks/`）、讨论纪要和决定（`docs/` 里 `kind: 纪要`，`decisions/`）、会话、时间线。

任务挂在研究视图的某一步上（`about`），例如「验证小环境能否代替完整训练」是一次尝试，下面可以有「设计比较方案」「跑实验」「写分析」三张任务卡；跑实验的任务又会产生多次运行。

控制台忽略 `board/` 里本文件没有提到的内容（例如 `FORMAT.md`、`legacy-site/`）。

## 层级

控制台按这条线组织项目：

```
实验设置（setup.json）
  └ 版本（versions/）：定版时的方案
      └ 支线（tracks/）：从某个版本分出来、或者并入某个版本
          └ 尝试（attempts/）：按时间先后
              ├ 运行（runs/）：数字都在这里
              └ 例子：一条真实样例
```

链接靠各条目的 `id`：尝试的 `track` 指向支线，支线的 `from_version` 和版本的 `merged_tracks` 把支线挂到版本上，尝试的 `runs` 和运行的 `attempt` 互相指向（控制台取两边的并集）。

## Markdown 记录文件（versions、tracks、attempts、plan、docs）

开头是一段字段区：第一行 `---`，若干行 `key: value`，再一行 `---`，之后是正文。值只有三种写法：纯文本、`[a, b]` 形式的列表、`null`。没有嵌套；行内「空格 + `#`」之后是注释。

- **versions**：`id`, `date`, `title`, `parent`（上一个版本或 `null`）, `merged_tracks`（列表）。正文是这个版本的方案：和上一版相比改了什么、为什么。可以有一节「## 结论」：这个版本得出的结论；控制台用当前版本的这一节作为项目的当前结论（没有时才用 `project.json` 的 `conclusion`）。
- **tracks**：`id`, `title`, `status`（进行中 / 暂停 / 并入主线 / 放弃）, `from_version`, `started`, `ended`。正文二级标题：假设、现状、结局和原因。
- **attempts**：`id`, `track`, `date`, `status`, `runs`（列表）, `task`（可选：哪张任务卡在做它）, `after`（可选，列表：这次尝试接在哪几次尝试之后，例如在它们的结果上改进；不写就按同一支线里的日期先后），`status` 为「待确认」时可加 `proposed`（建议的结论：成功 / 部分成功 / 失败 / 放弃，控制台标成「建议」）。正文二级标题依次为：一页纸、假设、预期、改了什么、结果、例子、结论和原因。

attempts 的 `status`：
- 计划中：讨论方案时定下要做、还没开始。写好假设和预期，`date` 写计划日期或留空。控制台在流程图上画成虚线节点。
- 进行中：还在做，结果没出来。
- 成功：假设成立。
- 部分成功：假设在某些条件下成立、某些条件下不成立；「结论和原因」里分开写成立的条件和不成立的条件。
- 失败：假设不成立，或者没有跑成。
- 放弃：决定不再继续这个方向。这是决定，不是结果。
- 待确认：结果已有，结论等用户定。

开新支线、关闭支线、定新版本、给一次尝试下「成功 / 失败 / 放弃」的结论，都由用户确认；起草时用「待确认」。

### 「一页纸」一节（放在最前面）

用户打开一次尝试先看到的五行，回答「这个实验干了什么」。用大白话，不用没解释过的术语（术语在 `setup.json` 的 `terms` 里解释一次）。

```
## 一页纸
- 想回答：只用 1/4 训练数据的「小环境」比较配方，排出的名次和完整训练一样吗？一样的话，之后每次训练便宜约 4 倍。
- 怎么做：6 个配方在小环境里各训练一次（团队配方训练 3 次看波动），把名次和完整训练对比。
- 预期：大致一致，排名相关 0.8 以上（用户在控制台选的）。
- 结果：基本无关，排名相关 0.09。最明显的：「批大小减半」在完整训练里和团队配方打平，小环境里垫底。
| 名次 | 完整训练 | 小环境 |
|---|---|---|
| 1 | mammoth-1 | mammoth-1 |
| 6 | Brier 3 | 批大小减半 |
- 所以：小环境不能用来比较配方；下一步的选项在待办 small-env-next。
```
- 五项固定：想回答、怎么做、预期、结果、所以。每项一行，一两句（不超过 150 字）。
- 「想回答」「怎么做」「预期」从计划时就写；「结果」「所以」在有结果后写（状态是成功、部分成功、失败、放弃、待确认时必须有）。还没结果时「结果」可以写「还没出」。
- 「结果」里给一个最能说明问题的具体例子或数字（数字可以用 `{{run:...}}` 引用）。某一项下面可以接一张小表（不超过 10 行）或几行补充，其余细节放到后面各节。
- 用户没写预期时，「预期」写「用户没写」；用户说猜不到时，给几个选项让用户选（例如「A 基本一致 / B 只认得出大的差别 / C 基本无关」），选不出来说明实验还没讲清楚，先讲清楚再开始。

### 「结果」一节：只写解读，不抄数字

数字只存在运行记录（`run.json` 的 `metrics`）里。控制台会在尝试详情里，按 `display` 和 `setup.json` 的定义，自动画出这次尝试关联运行的指标表和条形图。

所以「结果」一节：
- 先一两句话说发生了什么，例如「新策略条款上准确率明显下降，其余三个测试集持平」。
- 再写运行记录里没有的东西：和预期的对照、观察到的现象、跨运行的比较结论。
- 不要手抄指标表。正文里需要引用某个数时，写成引用：`{{run:<运行编号>/<分组>/<指标>}}`，例如 `{{run:eval-kev_fixed/authz_test_iid/accuracy}}`。控制台显示运行记录里的值并链接到这次运行；运行重跑或改了，正文不用改。
- 指标的定义写在 `setup.json` 的 `metrics` 里，不在每篇尝试里重复。

同样的规则适用于支线和版本的正文：控制台会在支线页和版本页自动给出「各次运行 × 各测试集」的主指标表，正文只写解读。

区分「测出来的」和「定下来的」：
- 测出来的结果（指标、用时、步数、见过的记录数、显存峰值等）只记在 `run.json`，正文不抄。
- 定下来的设计和设置（学习率、轮数、批大小、用哪个基座、各组之间有什么不同）可以写在正文里，读的人需要它们来理解这次尝试；它们不会在运行之后被重算。

### 「例子」一节

一条真实样例，说明这次尝试具体做了什么。放在「结果」之后、「结论和原因」之前。
- 依次写：原始记录的关键字段、模型看到的输入（可以节选）、模型的输出、怎么计分、判对还是判错。
- 用列表或小表格，几行就够，不要原样贴整条 JSON。
- 样例来自 `examples/probe.jsonl` 时，写明它的 id。
- 调试类或失败在半路的尝试没有合适样例时，写一句「没有可展示的样例」和原因。

## project.json

```
{"name", "title", "question", "conclusion", "status", "current_version", "updated", "display"}
```
- `status`：进行中 / 暂停 / 已归档。
- `question`：研究问题；`conclusion`：当前一句话结论。
- `display`（可选）只影响控制台怎么显示，不影响数据：
  - `default_group`（字符串）：运行页默认选中的分组。
  - `group_order`（字符串列表）：分组按钮的顺序，列出的排前面，其余按运行数从多到少排。最多显示 6 个按钮，其余进下拉框。
  - `primary_metrics`（字符串列表）：默认显示的列，列名相对于分组，嵌套的用点号连接。其余列收进「显示全部列」。
  - `ratio`（`{显示列: [分子列, 分母列]}`）：分子分母都有值时，单元格显示成「0.5997 (361/602)」，默认隐藏分子列和分母列。写之前核对该显示列确实等于分子 / 分母。
  - `headline`（`{"group", "metric", "better"}`）：概览页「最好的主指标」卡片取哪个数，`better` 取 `"higher"` 或 `"lower"`。`kind` 为 data 或 smoke 的运行、以及同组里 `n` 小于 `of` 的抽查运行不参与。
  - 不认识的字段、类型不对的值会被忽略，并在页面上提示。

## setup.json

论文里的「实验设置」一节，显示在项目概览页；运行页的分组名和表头的指标名会链接到这里的定义。

```
{"goal": "一两句：想弄清楚什么、做成什么样算回答了",
 "datasets": [{"id", "name", "role", "size", "about", "source"}],
 "models":   [{"id", "name", "version", "about"}],
 "metrics":  [{"id", "name", "better", "about"}],
 "methods":  [{"id", "name", "track", "runs", "about"}]}
```
- `datasets[].id` 必须和 `run.json` 里 `metrics` 的第一层键（分组名）一模一样。`role` 取 `train`、`dev`、`calib`、`test`、`other`。
- `metrics[].id` 必须和分组下的列名一样。`better` 取 `"higher"`、`"lower"` 或 `null`（不分好坏，例如条数）。
- 编号的指标或分组用 `{n}` 统一定义一次：`acc_step{n}` 覆盖 `acc_step1`、`acc_step2`……；`val_sub{n}` 覆盖 `val_sub1`……（`{n}` 只代表数字）。
- `terms`（可选）：`[{"term": "配方", "about": "一整套训练设置：模型、学习率、数据增强、训练轮数等"}]`。项目里会反复出现、用户可能不熟的说法，每个一句白话（不超过 120 字）。控制台在正文里给这些词加下划线，鼠标放上去显示解释。
- `models[].version` 写到能复现的程度，例如仓库名加 revision。
- `methods[].track`（可选）把方法和支线连起来；`methods[].runs`（可选）列出属于这个方法或对照组的运行编号，控制台在表格和图里用方法名代替运行编号。方法名用论文里会写的说法，12 个字以内。
- 除了 `id` 和 `name`，其他字段都可以不写。`about` 一两句，不写长段落，不贴原始字典。
- 研究问题本身写在 `project.json` 的 `question` 里。

## run.json

**由运行自己写，不手写。** 训练、评测、数据处理脚本用记录模块 `boardrun`（共享盘 `/shared/ssd/dchen/_shared/tools/boardrun`，项目里 `uv add --editable /shared/ssd/dchen/_shared/tools/boardrun`）：

```python
import boardrun
with boardrun.Run(attempt="<尝试 id>", kind="train", config=cfg) as run:
    run.log(step, loss=loss)                  # 曲线 -> metrics.jsonl
    run.result("<分组>", accuracy=acc, n=n)   # 最终指标 -> metrics[分组]
    run.sample(id=..., output=..., score=...) # 样例 -> samples.jsonl
    run.artifact("curve.png")                 # 小图复制到运行目录
    out = run.output_dir()                    # results/<运行编号>/：大输出，控制台不显示
```
正常结束记「完成」，抛异常记「失败」并写明错误，Ctrl-C 或 SIGTERM 记「被中断」。服务器、卡号、进程号、tmux 会话名、commit 自动填。不是 Python 的命令：`python -m boardrun run --attempt <尝试 id> --kind eval [--task <任务 id>] -- <命令>`，按退出码记状态并写下 `exit_code`。续跑用 `resumed_from=<上一次的运行编号>`，会得到新编号。

- **每次运行绑定一个提交。** 代码有未提交的改动、或者还没有任何提交时，boardrun 拒绝启动（`DirtyCode`，命令行退出码 3），不会留下运行目录。先提交再跑；只有调试时才加 `allow_dirty=True`（`--allow-dirty`），这时 commit 带 `-dirty`。代码在项目里的另一个仓库（例如团队仓库的克隆、`.worktrees/<任务>`）时，从那个目录里启动，记的是那个仓库的提交，并写下 `code_dir`。
- **心跳。** 运行期间每分钟写一次 `runs/<运行编号>/heartbeat`。控制台据此区分「运行中」和「状态未知」；收尾程序（a100 上每 5 分钟一次的 `board reconcile`）对心跳停了 5 分钟以上的运行去机器上查进程（每台机器一次 ssh），连续两次都查不到才把记录改成「被中断」，并写 `closed_by: board reconcile`。
- `task=<任务 id>`（`--task`）：这次运行属于哪张任务卡。任务卡是「等运行」时，它的运行都结束后，收尾程序把卡改成「可以继续」。

运行记录了 `attempt`，尝试的 `runs` 列表就可以不写（控制台两边都认）。下面是字段说明；没接入模块的旧运行照这个格式手写。

```
{"id", "kind", "attempt", "task", "status", "server", "gpus", "pid", "tmux", "started", "ended", "exit_code", "commit", "code_dir", "resumed_from", "config", "metrics", "artifacts"}
```
- `kind`：train / eval / data / smoke / 其他。`kind` 为 data 的运行在运行页单独成表。
- `status`：运行中 / 完成 / 失败 / 被中断。失败和被中断时可以有 `error`（一句话的原因）。控制台另外显示一个观测到的状态：运行中（心跳是新的或看到了进程）/ 状态未知（心跳停了、机器连不上，显示最后观测时间）/ 已结束 / 已中断（心跳停了、机器上也没有进程；收尾程序随后会把记录改成被中断）。手写的旧记录没有心跳，只能靠显卡上的进程判断。
- `commit`：代码的提交号；末尾 `-dirty` 表示运行时有未提交的改动。
- `metrics` 按「分组 → 指标」组织，分组通常是测试集，例如 `{"authz_test_iid": {"accuracy": 0.6, "correct": 361, "n": 602}}`。分组名和指标名要在 `setup.json` 里有定义。
- `config`、`artifacts` 是对象，控制台显示成两列的键值表。
- `metrics.jsonl`（可选）：每行一个 JSON，含 `step` 和若干数值；只追加写，最后一行没写完的会被跳过。
- `samples.jsonl`（可选）：样本输出，控制台显示前 20 行。
- 图片（可选）：`png`、`jpg`、`svg`，放在运行目录下，单个不超过 10 MB。

## examples/

- `walkthrough.md`：「一个例子」，一条样例从头走到底。开头放精简版，之后用一行 `---` 和一级标题「完整原文」隔开放完整原文；控制台默认只显示精简版。
- `probe.jsonl`：固定的观察样例，每行一个 JSON。

## flow.json（可选）

项目流程图，控制台画成从左到右的方框加箭头。

```
{"nodes": [{"id", "title", "subtitle", "group", "link"}], "edges": [["起点 id", "终点 id"]], "groups": {"组 id": "图例文字"}}
```
- 最多 8 个节点；`title` 不超过 8 个汉字，`subtitle` 不超过 12 个汉字。
- `group` 区分方框属于哪一类（例如「我们的代码」和「模型」），图例文字写在 `groups` 里。
- `link` 是控制台内部的位置，写法见下文「控制台内部链接」。

## tasks/<id>.md（任务卡：agent 要做的一件事）

工作视图的单位。一张卡是一件有明确交付物的事，由一个会话从头做到尾；做完写交接，下一个会话靠交接接着做。

```
---
id: f1-metric
title: 加 F1 指标并重算旧结果
kind: 执行
status: 进行中
about: a:2026-11-23-small-env-check
scope: [src/eval/, scripts/eval.py]
deliver: [每次运行的 run.json 都有 f1]
budget: 2 卡时
after: [data-fix]
sessions: [jev-fraud·f1-metric]
created: 2026-11-24
updated: 2026-11-24T06:00:00Z
---
## 要做什么
## 完成标准
## 交接
- 做了什么：
- 证据在哪：
- 没做完的：
- 下一步：
- 要你决定的：
## 结果
```
- `id`：英文短名，和文件名一致。会话名用「<项目>·<任务 id>」。
- `kind`：讨论 / 执行 / 写作 / 分析 / 审查 / 调试。
- `status`：
  - 待开始：卡写好了，还没人做。
  - 进行中：有会话在做。
  - 等运行：训练或评测已经启动，会话可以结束；运行都结束后收尾程序把它改成「可以继续」。
  - 等你：卡在用户这里（要决定、要批准用卡、要合并）。同时在 `todos.jsonl` 里留一条待办，`link` 写 `tasks/<id>`。
  - 可以继续：等的东西到了（运行结束、用户回复了），下一个会话接着做。
  - 完成 / 暂停 / 放弃。
- `about`（可选）：挂在研究视图哪一步上，写法同文档的 `about`。
- `scope`（改代码的任务要写）：允许修改的路径。范围重叠的两张卡不同时进行。
- `deliver`：交付物；`budget`（可选）：预计的卡时或其他预算，一句话。
- `after`（可选）：要等哪几张卡做完才开始。
- `sessions`：做过这张卡的会话名或会话 id，按时间先后。
- 正文：「要做什么」必须有；状态是完成、等你、可以继续时「交接」必须有。交接五项：做了什么、证据在哪（文件、运行编号、提交号）、没做完的、下一步、要你决定的。

### 开工、并行和合并

- **开工**：项目会话（或用户）在 a100 上运行 `/home/dchen/bin/board task-start <项目> <任务 id>`。它在 tmux `task-<项目>-<任务 id>` 里起一个会话，名字是「<项目>·<任务 id>」，开着远程控制（用户在 App 里点它就能插话），开场就读任务卡做事。`board task-stop <项目> <任务 id>` 停掉它。
- **上限**：所有项目加起来同时最多 4 个任务会话（含自动处理回复的会话）；同一个项目同时只做一张改代码的卡（kind 是执行或调试）。超了 `task-start` 会拒绝并说明原因。
- **改代码的卡**（执行、调试，且写了 `scope`）：在 `<项目>/.worktrees/<任务 id>`（分支 `task/<任务 id>`）里改和提交，不动主目录；`.worktrees/` 写进 `.git/info/exclude`，不进版本库。运行从 worktree 里启动，记的是 worktree 的提交。
- **记录一律写主目录的 `board/`**：worktree 里也有一份 `board/`，那份不用。
- **合并**：收尾时先 rebase 到主线、跑测试。没动核心代码（项目 `CLAUDE.md` 里列的目录）且没有冲突，就合并回主线、删掉 worktree；动了核心代码或有冲突，把卡改成「等你」，在待办里请用户选「合并 / 再改 / 放弃」。
- **不写代码的卡**（讨论、写作、分析、审查）在项目主目录里做，产物放 `outputs/<任务 id>/` 或 `board/docs/`。
- **等训练**：用 boardrun 启动（`--task <任务 id>`），卡改成「等运行」，写好交接就可以停下；运行都结束后收尾程序把卡改成「可以继续」。

## decisions/<id>.md（决定）

用户定下的事。讨论中的想法先记成「候选」，用户在控制台点「采纳」才生效；生效的决定会写进每个新会话的事实包，所以不会被忘掉。

```
---
id: small-model-first
title: 先用 9B 跑通，再上 27B
status: 候选
replaces: [both-sizes]
about: v:v1
date: 2026-11-24
source: docs/2026-11-24-discussion-scale.md
---
## 决定
一句话写定了什么。
## 理由
## 影响
```
- `status`：候选 / 采纳 / 不采纳 / 已替代。会话只写「候选」；用户在控制台的回复（`answers.jsonl` 里 `d:<id>`）立即生效，处理回复时再把文件里的 `status` 改过来。被一条已采纳的决定 `replaces` 的旧决定自动算「已替代」，旧文件保留。
- 一条决定只写一件事。用户在对话里说的长期有效的话（例如「这是团队项目」「预期不写」）也记成决定。
- `source`：出处（讨论纪要的文件，或待办 id）。

## 讨论纪要（docs/，kind: 纪要）

一段讨论告一段落（定了事或得出新结论）时写一篇，`about` 写讨论的是哪一步，`decisions` 列出这次产生的决定：

```
---
title: 讨论：先跑小模型还是两个一起
about: v:v1
kind: 纪要
decisions: [small-model-first]
---
## 讨论了什么
## 考虑过的做法

## 为什么
## 还没定的
```

## todos.jsonl

留给用户的待办，让用户不用自己记要做什么。每行一个 JSON：

```
{"id", "text", "kind", "where", "created", "done", "by", "link", "context", "options", "recommend", "result"}
```
- `text`：一句话的问题或要做的事。
- `kind`：`"blocking"`（卡着进度）、`"decision"`（等用户做决定）、`"whenever"`（不急）。
- `context`：可选，回复需要知道的背景（Markdown，两三行）：现在的情况、每个选项的后果和代价。让用户在控制台上不用翻别的记录就能回复。
- `options`：可选，回复的选项，字符串列表，每项一句短话，例如 `["现在补（1 张卡约 20 分钟）", "先不补"]`。有选项时控制台显示成按钮。
- `recommend`：可选，建议选哪一项，必须和 `options` 里的某一项完全相同。
- `where`：可选，不在控制台回复时去哪里做，例如「h100 会话」。
- `created`、`done`：ISO 8601 UTC；`done` 为 `null` 表示没做完。
- `result`：标记完成时写一句做了什么，例如「已在 h200 卡 2 启动 r012」「按回复不补，记进尝试 focal」。
- `by`：写这条的会话；`link`：可选，控制台内部链接。
- `state`：可选，处理回复的进度：`已领取`（会话开始处理这条）、`受阻`（处理不下去，`result` 写原因，并另留一条待办问用户）。控制台在回复旁显示。
- 同一个 `id` 出现多行时以最后一行为准。标记完成只需追加一行 `done` 不为 `null` 的记录（带上 `result`），不改写旧行。
- 跨项目的待办放在 `/shared/ssd/dchen/_shared/todos.jsonl`，格式相同。

任何会话给用户留下一件要做或要决定的事，都在对应项目的 `todos.jsonl` 里追加一条；能给选项的就给选项和建议。

## method/*.md（方法：怎么做，一步一个文件）

论文里「方法」一节的流程图：从输入到输出分几步，每一步怎么做。控制台「方法」页把它画成一层层可以点开的方框图，并和实验互相链接（实验流程记的是「试了什么」，方法记的是「怎么做」）。

```
---
id: gepa
title: GEPA 优化提示词
variant_of: prompt
tracks: [gepa]
methods: [jev_gepa]
---

## 一句话
不动权重，让强模型根据错题改写问题说明和判据。

## 输入和输出
## 怎么做
## 关键设置
## 例子
```
- `id`：步骤的 id（英文、数字、连字符）。
- `parent`：这一步属于上一层的哪一步（它是那一步的子流程）。顶层步骤不写。
- `next`：列表，同一层里接下来是哪几步，控制台画成箭头；同一层按箭头排先后。
- `back`、`loop`：可选，循环。`back` 写同一层里前面某一步的 id，表示做完这一步回到那一步重复；`loop` 写次数或条件，例如 `30 轮`。控制台把循环的几步标出来，回环不影响按 `next` 排先后（`next` 照常指向循环结束后的下一步）。
- `variant_of`：这一步是另一步的不同做法（例如「输入」这一步有「通用提示词」和「GEPA 优化提示词」两种）。变体和原步骤在同一层，不写 `parent`；变体自己可以有子流程（子步骤的 `parent` 写变体的 id）。
- `tracks`：列表，在试这一步（或这种做法）的支线。控制台据此列出「试过它的实验」及其结果；尝试也可以在字段区写 `method: [步骤 id]`。
- `methods`：列表，对应 `setup.json` 里 `methods` 的 id。
- 正文小节：一句话、输入和输出、怎么做、关键设置、例子。数字用 `{{run:...}}` 引用。
- 一层建议不超过 6 步，太细的放进子流程。
- 讨论或更新方案时同步写；有了 `method/` 之后，`flow.json` 可以不再维护。

文档也可以属于方法的某一步：`about: m:<步骤 id>`。

## docs/*.md（文档）：属于哪一步、什么类型

每篇文档开头写字段区，控制台据此把文档挂到流程图对应的那一步上，文档页按流程顺序归类：

```
---
title: 第 1 轮复盘
about: a:loop-txhist-v0-r1
kind: 复盘
replaces: [options-v0]
---
```
- `about`：这篇文档属于哪一步：实验流程里的 `v:<版本 id>`、`t:<支线 id>`、`a:<尝试 id>`，方法里的 `m:<步骤 id>`，或工作视图里的 `k:<任务 id>`、`d:<决定 id>`。不写表示属于整个项目（例如团队简介、总体设计）。
- `kind`：方案（做之前：设计、计划、选项）/ 观察（做的过程中记下的现象）/ 复盘（一轮做完后的总结）/ 报告（给别人看的结果汇总）/ 说明（参考资料、操作说明）/ 纪要（一段讨论的记录，见上文）。
- `replaces`：可选，这篇取代了哪几篇旧文档（写文件名，不带 `.md` 也行）。旧文档保留，控制台把它标灰并指向新的。改动大的方案不要直接覆盖旧文件，新写一篇用 `replaces` 指向旧的。
- `title`：可选，不写就用文件名。

`plan.md` 自动算作「整个项目 · 方案」；根目录的 `NOTES.md`、`REPORT.md` 算作整个项目的笔记和报告。

## marks.jsonl（用户对文档的标记）

用户在控制台文档页把文档标为「看过」或「确认」，追加到 `board/marks.jsonl`。**只由控制台写，会话只读。**

```
{"file", "mark", "at", "mtime", "by"}
```
- `file`：文档路径，例如 `docs/r1-review.md`、`plan.md`、`NOTES.md`。
- `mark`：`"看过"`、`"确认"`，或 `null`（清除标记）。同一 `file` 以最后一行为准。
- `mtime`：标记时文档的修改时间；之后文档又改过，控制台显示「有更新」。
- 「确认」表示用户认可这篇的内容。被确认的文档，会话要改内容之前先问用户，或者新写一篇用 `replaces` 指向它。

## answers.jsonl（用户在控制台上的回复）

用户在控制台的待办页或项目概览上回复待办、确认尝试的结论。回复追加到项目的 `board/answers.jsonl`（跨项目待办的回复在 `_shared/answers.jsonl`）。**这个文件只由控制台写，会话只读不改。**

```
{"id", "answer", "text", "at", "by"}
```
- `id`：待办的 `id`；确认尝试结论时是 `a:<尝试 id>`；采纳决定时是 `d:<决定 id>`。
- `answer`：选中的选项（待办的某个 `options`；尝试是 成功 / 部分成功 / 失败 / 放弃；决定是 采纳 / 不采纳），没选为 `null`。
- `text`：用户的补充说明，可以为空。
- `mode`：可选，`"直接处理"` 表示用户勾了「直接处理」：a100 上的派活程序（`board dispatch`，每 5 分钟）会为这条起一个会话自动处理，不用等用户说「处理回复」。没有这个字段的回复照旧等用户说。
- 同一个 `id` 有多行时以最后一行为准（用户可以在会话处理前改回复）。

**处理回复**：只在用户说「处理回复」时处理（`mode` 是「直接处理」的由派活程序起的会话处理），不要自己开始。会话开始时如果有未处理的回复，提一句有几条。处理时：
1. 读 `answers.jsonl`，只看还没处理的：对应待办在 `todos.jsonl` 里 `done` 还是 `null`，或对应尝试还是「待确认」。
2. 逐条先复述你理解的回复和打算怎么做（开始处理一条时，在 `todos.jsonl` 追加这条的一行，`state: 已领取`）；回复有歧义、或和当前情况冲突时，先问用户（`state: 受阻`）。
3. 待办做完后，在 `todos.jsonl` 追加这条的完成行，写 `done` 和 `result`。要很久才能做完的（例如启动了训练），启动后就标完成，`result` 写启动了什么。
4. 尝试的结论：把 `status` 改成用户选的结论，用户的补充写进「结论和原因」；之后如果还留着与这次确认有关的待办，一并标完成。
5. 决定：把决定文件的 `status` 改成用户选的（采纳 / 不采纳）。

## 控制台内部链接（flow.json、todos.jsonl 的 link）

写成「分页[/条目][?筛选]」：
- `overview`：项目概览（含实验设置）
- `roadmap`：路线。条目写 `v:<版本 id>`、`t:<支线 id>` 或 `a:<尝试 id>`，例如 `roadmap/a:2026-11-10-kev-fixed`
- `runs`：运行，条目是运行编号，例如 `runs/eval-kev_fixed`
- `examples`：样例
- `docs`：文档，条目 `plan` 是整体方案
- `tasks`：任务，条目是任务 id，例如 `tasks/f1-metric`
- `decisions`：讨论与决定，条目是决定 id

旧写法继续可用：`experiments/<尝试 id>` 等于 `roadmap/a:<尝试 id>`，`experiments?track=<支线 id>` 等于 `roadmap/t:<支线 id>`。

## 控制台会检查什么

项目概览页底部的「记录检查」列出写记录的会话可以自己修的问题：
- 尝试的 `track` 指向不存在的支线；`runs` 里有不存在的运行；运行的 `attempt` 指向不存在的尝试。
- 支线没有挂到任何版本上（没有有效的 `from_version`，也不在任何版本的 `merged_tracks` 里）；`merged_tracks` 里有不存在的支线。
- 运行里出现的分组或指标没有在 `setup.json` 里定义；`setup.json` 的方法引用了不存在的支线或运行。
- 尝试没有字段区，没有「例子」一节（计划中的除外），或者「一页纸」缺项、写得太长。
- 任务卡、决定的字段写错（类型、状态不认识，指向的任务、决定、尝试不存在，文件名和 id 不一致），缺必需的一节；两条已采纳的决定替代同一条。
- 文档没有 `kind` 或 `kind` 不认识；`about` 指向不存在的记录；纪要的 `decisions` 里有不存在的决定。
- `setup.json` 的 `terms` 缺解释或解释太长。
- `display.headline` 指向的分组和指标在运行记录里找不到。
- 读不了的文件（JSON 写坏、待办行缺 `id` 或 `text` 等）。

## 正文怎么写

只管表达形式，不改变事实。
1. 每个二级标题下先用一两句话说结论性的事实，再放表格和细节。
2. 不把程序里的原始字典或 JSON 贴进正文；写成人能读的话或小表格。
3. 表格不超过 5 列，超过就拆开；数字列写「分子/分母」，可带比率。
4. 并列的几件事用列表，一条一件；一段话不超过三四行。
5. 术语在 `setup.json` 的 `terms` 里解释一次，正文保持同一种叫法。
6. 用户确认过的结论保留确认标注（谁、哪天、经谁转达）；回填的记录在「预期」里写明是回填。
7. 可用的 Markdown：标题、表格、列表、行内代码、加粗、代码块、引用、分隔线。

## 通用约定

- 时间用 ISO 8601 UTC。
- 除 `metrics.jsonl` 和 `todos.jsonl` 这类只追加的文件外，先写临时文件再改名（共享盘是 soft 挂载）。
- 只写有出处的事实；查不到的字段填 `null`。
- `board/` 是私人记录，不放进团队共享的仓库或站点。
